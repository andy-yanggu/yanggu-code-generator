# Spec 模板 v1（yanggu-code-generator 项目适配版）

> **用法**：复制本文件为 `docs/superpowers/specs/YYYY-MM-DD-<主题>.md`，删掉所有 `<!-- 说明 -->` 注释块后填写。
> **实施计划另出**，放 `docs/superpowers/plans/YYYY-MM-DD-<主题>.md`（沿用仓库现有惯例）。

---

## 五条硬规则（模板的立身之本，违反则本 spec 无效）

| # | 规则 | 违反后的真实后果 |
|---|---|---|
| 1 | **一份 spec 只覆盖一个连贯变更**；目标里出现"并且/同时/顺便"就拆开 | 部分完成无法被发现，AI 会声称"已完成" |
| 2 | **每条 AC 必须配一个可执行验证命令**；写不出命令的 AC 要么改写成可观测结果，要么删掉 | "已完成"变成主观判断，人工 review 成为唯一防线 |
| 3 | **约束必须显式写出**；未写的约束 AI 会用猜测填补 | 凭空引入依赖、擅自扩大改动面、破坏未登记的冻结范围 |
| 4 | **Out of scope 必须写** | "顺手改一下"式蔓延，回归面失控 |
| 5 | **范围一变就改 spec**，不允许代码与 spec 分叉 | 陈旧 spec 比没有 spec 更危险（假信心） |

## 3. Constraints（约束）

<!-- 说明：约束是需求的一部分，不是建议。AI 猜出来的约束会偶发违反且不会报错。 -->

### 3.1 项目固有约束（不可协商）

- ⚠️ **模板类约束会过期**：本项目曾有“v1 `tree.vue` 冻结 / v1与v2 双跑对照”约束，但 v1 已于 `4a27750b` **删除**。
  写约束前必须先用 `git cat-file -e "HEAD:<路径>"` 确认引用的文件**还存在**；已删除的基线不得再当对照依据。
  同时：**不要回改历史设计文档**（它们是变更快照），只在现行 spec 的 §11 登记为已过期。
- **分层原则**：数据域零弹窗；弹窗与提示只允许出现在编排层 `use-template-tree-state.ts`。
- **纯函数惯例**：`tree-utils.ts` / `variable-utils.ts` 内函数不得依赖响应式；依赖外部查询时用参数注入（如 `findById`）。
- **ESLint**：`func-style` 规则强制函数表达式写法。
- **测试环境**：`vitest.config.ts` 为 `environment: 'node'`，`include: ['src/**/*.{test,spec}.ts']`；组件级测试需在测试文件顶部声明 `// @vitest-environment jsdom`。
- **前端无 Playwright**：当前 e2e 依赖 browser MCP 手工执行，因此涉及 UI 的 AC 必须成对拆分「逻辑层（可单测）」+「表现层（人工/待自动化）」，禁止用一条 UI 级 AC 承载可单测的逻辑。
- **后端**：Java 21 / **Spring Boot 4.1.2** / MyBatis-Plus 3.5.18 / FreeMarker；starter 命名已迁移（`spring-boot-starter-webmvc`）；
  模板渲染涉及 FreeMarker 沙箱（`?new` 已禁用）与 Oracle/MySQL 方言分支（**后端零 DB 集成测试覆盖**）。

## 5. Acceptance Criteria（验收标准）

**填写规则**：
- `AC-ID`：`AC-<主题缩写>-<序号>`，供 plan 与测试反向引用。
- `验证命令`：**必须能复制即跑**；填绝对路径或 `pnpm/npm/mvn` 命令。
- `层级`：`unit` / `contract` / `integration` / `e2e-auto` / `e2e-manual` / `static` / `review` / `metric`
- `状态`：`✅ 可跑` / `🟡 待补` / `⬜ 暂无法验证`
- **规则**：`e2e-manual` 与 `review` 只能作为临时状态，必须在 §8 登记为待自动化项。
- **规则**：逻辑类 AC 不许直接写 `e2e-manual`，先尝试下沉到 `unit`。

| AC-ID | 验收标准（可观测结果） | 验证命令 | 层级 | 状态 | 覆盖情况 |
|---|---|---|---|---|---|

### 5.2 怎么写一条合格的「验证命令」

> 本节来自模板首次落地时的真实翻车案例，规则从这里来。

| 规则 | 说明 |
|---|---|
| **复制即可跑** | 必须能在项目根目录直接粘贴执行。含占位符的（`<BASE>`）要在 §0 元信息里给定来源 |
| **断言「变化」而非「状态」** | 最容易犯的错。约束若是「**新增**代码里不许有 X」，命令必须基于 **diff**，而不是全文 grep——因为同类代码在**别的功能**里可能本来就该有，全文匹配必然假阳性 |
| **先跑一遍再写进 spec** | 未实测的命令不许入表。命令跑通 ≠ 断言正确，两者都要验 |
| **一条 AC 一个命令** | 合并命令会让失败无法定位到具体 AC |
| **禁止用自然语言当命令** | 「人工确认」「浏览器实测」「review 一下」不是命令 → 必须落到 `层级=e2e-manual/review` 并进 §8 债务台账 |
| **验证命令自己也要过 test** | 除跑通外，需构造**负向例**（应无输出）与**正向例**（应命中）各一次。只跑负向例会漏掉"命令永远通过"的假绿 |
| **先验 pathspec 存活** | `git diff -- <不存在的文件>` **不报错**，而是返回空输出且 exit 0（已实测，`--exit-code` 也一样）。所有一切“diff 必须为空”类断言必须：① 先 `git cat-file -e "HEAD:<路径>"`；② 用 `--exit-code` 断言退出码而不是用肉眼判“没输出”。详见 pitfalls P-022 |
| **PowerShell 管道别用反引号续行** | `... \`` 换行接 `\| Select-String` 会让管道符被当字符串解析而报错；写成单行 |

**反例 vs 正例**（本项目真实案例）：

```powershell
# ✗ 反例：断言「组件层不许有弹窗」——tree-panel.vue 的删除链路本来就该有 ElMessageBox.confirm
#        全文匹配永远命中，假阳性，这条 AC 会一直显示为「失败」而被忽略
Select-String -Path tree-panel.vue,editor-panel.vue -Pattern "ElMessageBox|ElMessage\."

# ✓ 正例：断言「本次新增的行里不许有弹窗」——基线合规代码被自动排除，只有越界新增才会命中
# （写单行；PowerShell 反引号续行接管道会报错）
git diff <BASE>..HEAD -- ".../tree-panel.vue" ".../editor-panel.vue" | Select-String -Pattern "^\+.*(ElMessageBox|ElMessage\.)"
```

**上述正例已在本项目双向验证**：

| 验证方向 | 执行方式 | 预期与实际 |
|---|---|---|
| **负向**（应无输出） | 对无改动的工作区执行 | ✅ 无输出，存量合规代码被正确忽略 |
| **正向**（应命中） | 在真实引入弹窗的 commit（`63110161`）上执行 | ✅ 命中 **6 行**新增（`ElMessage.warning` / `ElMessageBox.confirm` / `ElMessage.success` 等） |

> 只跑负向例不足以证明命令有效——它可能只是写错了永远返回空。**双向都跑一次，花 30 秒，但挡掉"假绿门禁"。**
